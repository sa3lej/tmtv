# tmtv 3.0.0

This release moves the terminal core to the pinned tmux 3.8 source and introduces
sharing protocol 11. **Upgrade hosting clients and relays together.** It is not
wire-compatible with tmtv 2.x or earlier develop protocol versions.

## Terminal sharing

- Unicode keystrokes travel as Unicode scalars rather than process-local tmux
  identifiers, including emoji and private-use characters. Modifiers are retained.
- Pasted UTF-8 travels as literal bytes. Bracketed-paste delimiters are forwarded
  only when the application has enabled bracketed paste.
- Layout and snapshot transfers are bounded and validated. Unencodable layouts
  end sharing with an explicit error instead of leaving viewers out of sync.
- Reconnect restoration covers terminal state, OSC 8 hyperlinks and SIXEL images.
  Browser initialization waits for the image decoder before replaying output.

The snapshot limits and unsupported states are described in
[snapshot-protocol.md](../snapshot-protocol.md). Local terminal operation does
not require a sharing connection.

## Upgrading

For the public service, follow the operator's announced cutover time. Download
the new host binary in advance, but keep the previous binary until the relay has
switched. A v3 host cannot share through a v2 relay, and a v2 host cannot share
through a v3 relay. Ordinary SSH viewer applications require no tmtv installation.

For self-hosted installations, prepare both binaries and matching web assets,
then switch the relay and hosting clients in a planned maintenance window.
Restart running hosting processes after upgrading; replacing the executable
alone does not update those processes. Save work first: restarting a host ends
its local tmux server and may terminate programs in its panes. A fresh host
creates new sharing credentials and links. Automatic reconnects of the same
running host retain their identity, but a relay upgrade does not migrate live
sessions between incompatible versions.

Keep the old host, relay and web assets for rollback. Restore them together and
restart hosts with the old binary; new-version sessions and links cannot be
preserved by that rollback. See [the release procedure](../releasing.md).

## Release validation

The Build workflow exercises all twelve release binaries, verifies their exact
manifest and checksums, and gates publication on isolated authenticated relay
and Chromium, Firefox and WebKit checks. Develop validation separately covers
Linux and native Intel/Apple Silicon host regressions. Linux WebKit coverage
is not a claim of native Safari validation.

Release publication and production deployment are separate operations. Download
availability does not mean the public relay has switched; operators announce
that transition. Native Safari and deployed staging validation must be recorded
for the final candidate before production rollout.
